Overview

Matchstick (MGDF) provides tools to develop, distribute, and update C++ games on Windows. It provides DirectX 12 rendering with OpenXR VR support, OpenAL audio, XInput gamepad input, and HTTP/S and WebSocket networking support. Its virtual file system gives modules access to files on disk and in archives.

MGDF makes developing games in c++ faster and easier as you no longer have to build and rebuild the same boilerplate code for initializing DirectX/Audio etc, loading preferences and setting up a render loop every single time you make a game. This means you can spend more time making your game. For distribution, MGDF has an optional updater and an optional crash reporter.

MGDF has three parts. The core runs the game. The updater and the crash reporter are optional. A game installer or a store client installs the game.

The core (core.exe)

This is written in c++ and is the part of the framework which actually runs the games. The core works by initializing the graphics/input/audio devices, loading up user preferences and setting up a multithreaded render/simulation loop before loading the user supplied game dll (known as a game module) and passing control on to that module. Once up and running the game module can then access the framework's functionality via a series of c++ interfaces (see the API reference for more details)

The module uses MGDF interfaces for audio, input, files, networking, and graphics settings. Call IMGDFCommonHost::GetD3D12Device to get the graphics device. Use IMGDFRenderHost on the render thread for frame data and rendering calls.

The updater (updater.exe)

The game shortcut of an installed game starts the updater. The updater asks the update service of the game for a newer version. If there is a newer version, the player can install it or play the current version. Then the updater starts core.exe. See Updating.

NOTE The updater is optional. A store build starts core.exe directly and does not ship updater.exe, because the store client updates the game.

The crash reporter (crashreporter.exe)

When the game crashes, the crash reporter shows a dialog. The player can send a crash report to the crash report service of the game. See Crash reports.

The updater and the crash reporter need .NET Framework 4.8. The core does not need it.

Building a new game

MGDF expects the game files in a standard folder layout inside the install folder. The layout is as follows.

  • crashreporter.exe [Optional]

  • ... other runtime files and folders

  • /game

    All games files should be placed inside this folder

      All game executable dlls should be placed inside this folder

      • module.dll [Required]

        This dll is required and provides an entry point for the host to create an instance of the game module.

    • /content

      • Any game data files should go in here. This folder serves as the root of the virtual file system and content outside this folder is not accessable

Module.dll

Module.dll is the actual entry point into your game. This dll requires a number of functions to be exported, and must be able to provide the mgdf host with an instance of the IMGDFModule interface in order for the host to be able to run your game code.

MGDF is multithreaded and runs two main threads, the Sim thread and the Render thread. The Render thread is responsible for all rendering, and the Sim thread is responsible for handling input, audio, game logic. It is important to handle the sharing of data between these threads in a threadsafe manner for a game to work correctly. For the most part this means minimizing the amount of shared state between the Sim and Rendering parts of your game and ensuring that appropriate locking strategies are in place.

One method for managing this is to use a Double Buffered game state, i.e. the Sim thread modifies the game state and on each tick makes a copy of the current game state (or as much of a copy as the renderer needs to do its job) and copies it into a buffer which the Render thread can pick up when it's ready to render the next frame. In this way the Sim and Render threads can operate mostly independantly of each other without having to worry about concurrency issues. By default the Render thread will not run more than once per Sim tick, so you don't have to worry about buffer underrun in this case either (though this behaviour is configurable - if you have a very slow Sim framerate and want to interpolate a single game state over several render frames - check out the host.interpolateFrames preference option in the Game.json API reference)

NOTE The SDK includes a sample visual studio game project in src/samples/EmptyGame. This project contains a game.json file and will create a compatible module.dll with a stub module class.

Implementing the IMGDFModule interface

Implement each method in IMGDFModule. The host calls ST methods on the simulation thread. It calls RT methods on the render thread. It can call Panic on either thread. MGDF interfaces use COM reference counting. Release each interface when you no longer need it.

Call IMGDFCommonHost methods to get the D3D12 device and command queues from either thread. IMGDFRenderHost inherits these methods. Call its GetCurrentFrame method on the render thread to get the back buffer and its render target view. The module creates its own depth buffers.

This example shows the module callbacks and resource access. Add the drawing commands described in Writing a D3D12 module. Local MGDF::ComObject values release their references when the method returns. If you keep resources between frames, release back buffer references in RTBeforeBackBufferChange. Release device resources in RTBeforeDeviceReset and RTShutDown.

Implementing main.cpp

Export GetGraphicsRequirements to fill MGDFGraphicsRequirements. Set MinFeatureLevel to the minimum D3D feature level and MinShaderModel to a D3D_SHADER_MODEL value. Set HDRFormat to the format that the module writes for HDR output. Zero selects scRGB. Set VR to TRUE only if the module renders both headset views and the window.

The host reads these requirements before it calls GetModule. This example requires feature level 11.0 and shader model 6.0. It keeps VR off.

{% highlight c++ %} #include "Module.hpp" BOOL APIENTRY DllMain( HMODULE hModule, DWORD ul_reason_for_call, LPVOID lpReserved ) { return TRUE; } extern "C" __declspec(dllexport) HRESULT GetGraphicsRequirements(MGDFGraphicsRequirements *requirements) { if (!requirements) return E_POINTER; *requirements = {}; requirements->MinFeatureLevel = D3D_FEATURE_LEVEL_11_0; requirements->MinShaderModel = D3D_SHADER_MODEL_6_0; return S_OK; } extern "C" __declspec(dllexport) HRESULT GetModule(IMGDFModule **module) { auto m = MGDF::MakeCom(); m.AddRawRef(module); return S_OK; } {% endhighlight %}

Window title

The game window shows the gameName from game.json. Call IMGDFCommonHost::SetWindowTitle to show a different title, for example the build configuration or the current level. The title is UTF-8. A null or empty title restores the game name.

Call it from the Sim thread or the Render thread. The host changes the title on the window thread, so the call does not wait for the window.

{% highlight c++ %} BOOL Module::STNew(IMGDFSimHost *host) { #if defined(_DEBUG) host->SetWindowTitle("My Game - Debug"); #endif return TRUE; } {% endhighlight %}

Writing a D3D12 module

Declare the module's graphics requirements as shown above. Use the device and queues to create resources, record commands, and submit each frame.

To render to a headset, follow the OpenXR VR guide. It covers opt-in, eye targets, controllers, and optional features. Keep drawing the window in VR.

Device and queue access

Use IMGDFCommonHost methods from either thread. GetD3D12Device returns an ID3D12Device10 reference. GetDirectQueue, GetComputeQueue, and GetCopyQueue return command queue references. The module owns these returned references. Release them before you acknowledge a device reset. The device can be null during a reset.

Use IMGDFRenderHost on the render thread. GetCurrentFrame fills an MGDFFrameInfo structure. GetFrameFence returns an owned reference to the frame fence. Release that reference when you no longer need it. Do not signal this fence.

MGDFFrameInfo supplies the current BackBuffer, BackBufferRTV, BackBufferDesc, and BackBufferIndex. The back buffer pointer is borrowed. Release any references you add before RTBeforeBackBufferChange returns. Get the current frame again after a back buffer change. The D3D12 swap chain uses one sample per pixel. The module creates its own depth buffers and multisample targets.

Frame contract

  1. Call GetCurrentFrame in RTDraw. The back buffer enters this callback in D3D12_RESOURCE_STATE_PRESENT.
  2. Record the module's command lists. Add a resource barrier before you use the back buffer as a render target. End each list that uses the back buffer with a transition to D3D12_RESOURCE_STATE_PRESENT.
  3. Execute the lists on the direct queue in RTDraw. The module submits its own lists. The back buffer must be in PRESENT state when those lists complete.
  4. The host calls Present after RTDraw. It then calls void RTAfterPresent(IMGDFRenderHost *host). Use this callback to submit background work that does not use the presented back buffer.
  5. After RTAfterPresent returns, the host resolves GPU counters. It then signals the frame fence on the direct queue with FrameOrdinal.

FrameOrdinal and FrameSlot stay fixed through RTAfterPresent. Work on the compute or copy queue needs explicit synchronization. Signal a module fence on that queue after its work. Add a wait for that value on the direct queue before RTAfterPresent returns. The host's frame fence covers that work only after this synchronization.

Frame resources and deferred release

The host permits two frames in flight. FramesInFlight is 2. FrameSlot equals FrameOrdinal % FramesInFlight. Keep a command allocator and other temporary resources for each frame slot. Use FrameSlot to select them. BackBufferIndex identifies the swap chain image and is separate from the frame slot.

The host waits for the previous use of a frame slot before it calls RTDraw. You can then reset that slot's command allocator and reuse its resources. This applies to work covered by the host's frame fence. Track other queue work with a module fence.

Record a resource's last FrameOrdinal when you submit its final use. Keep the resource in a deferred release list. CompletedOrdinal is the highest completed frame fence value when the host prepares the frame. Release the resource only when CompletedOrdinal >= lastUseOrdinal. Apply the same rule before you reuse upload memory or GPU descriptor storage. CPU return from RTDraw does not indicate GPU completion.

GPU counters

Use IMGDFRenderHost::CreateGPUCounter to time commands on a direct queue list. Pass an IMGDFMetric, the native command list, and an output pointer for IMGDFPerformanceCounter. Compute and copy lists are not supported.

For lists used with GPU counters, include MGDF/D3D12CommandList.hpp from include/MGDF/D3D12CommandList.hpp in the SDK. Use MGDF::D3D12CommandList::Create to create each list. Call Reset on the helper to start a new recording. Call Close on the helper to finish recording. Use Get to record commands, create counters, and submit the native list. Do not call Reset or Close through the native pointer. The counter needs the helper's recording state. An untracked list returns E_INVALIDARG.

Begin each counter scope while its list is recording. Release the scope before you close or reset the list. Execute that list in the same frame before RTAfterPresent returns. The host logs and discards a scope that ends after its list closes, resets, or passes the end of its frame.

This helper records and submits a timed clear from RTDraw. The caller supplies an open command list for the current frame slot. Keep that list and its allocator alive until the frame completes. Create the metric with IMGDFCommonHost::CreateGaugeMetric.

{% highlight c++ %} #include #include #include #include HRESULT DrawTimedClear(IMGDFRenderHost *host, ID3D12CommandQueue *directQueue, MGDF::D3D12CommandList &commands, IMGDFMetric *metric) { MGDFFrameInfo frame = {}; host->GetCurrentFrame(&frame); auto list = commands.Get(); MGDF::ComObject counter; HRESULT result = host->CreateGPUCounter(metric, list, counter.Assign()); if (FAILED(result)) return result; { MGDF::ComObject scope; result = counter->Begin(nullptr, scope.Assign()); if (FAILED(result)) return result; D3D12_RESOURCE_BARRIER barrier = {}; barrier.Type = D3D12_RESOURCE_BARRIER_TYPE_TRANSITION; barrier.Transition.pResource = frame.BackBuffer; barrier.Transition.Subresource = D3D12_RESOURCE_BARRIER_ALL_SUBRESOURCES; barrier.Transition.StateBefore = D3D12_RESOURCE_STATE_PRESENT; barrier.Transition.StateAfter = D3D12_RESOURCE_STATE_RENDER_TARGET; list->ResourceBarrier(1, &barrier); const float color[4] = {0.1f, 0.2f, 0.3f, 1.0f}; list->ClearRenderTargetView(frame.BackBufferRTV, color, 0, nullptr); barrier.Transition.StateBefore = D3D12_RESOURCE_STATE_RENDER_TARGET; barrier.Transition.StateAfter = D3D12_RESOURCE_STATE_PRESENT; list->ResourceBarrier(1, &barrier); } // Release the scope while the list is still recording. result = commands.Close(); if (FAILED(result)) return result; ID3D12CommandList *lists[] = {list}; directQueue->ExecuteCommandLists(1, lists); return S_OK; } {% endhighlight %}

Call Create(device, allocator) before the list's first use. This leaves the list open. For each later use, reset the completed frame slot's allocator first. Then call Reset(allocator) on the helper before DrawTimedClear. Return TRUE from RTDraw after a successful submission.

Build requirements

Build modules with Windows SDK 10.0.26100 or later. The MGDF headers need no other D3D12 headers. Modules use MGDF types and calls for VR and need no OpenXR SDK.

Upscaling, frame generation and low latency

A module can use NVIDIA DLSS upscaling and DLAA, DLSS frame generation (DLSS-G) and Reflex low latency through the MGDF API. The module uses only MGDF types.

In VR, DLSS can upscale each eye separately. Frame generation is off and GetMaxGeneratedFrames returns 0. Low latency sleep and frame markers have no effect. The saved preferences apply again when VR ends. See VR upscaling and latency.

The module does not request these features. The host starts them when the device supports them, and tells the module what is supported. The module:

  • Reads the supported modes from the render settings manager.
  • Selects the upscale mode and the render size.
  • Renders the inputs: jittered color, depth and motion vectors. Frame generation can also use a color image without UI (hudless) and a UI image.
  • Supplies the camera data for each frame.
  • Reports the frame markers inside its frame: simulation, input and render submit.
  • Shows the settings to the user, and keeps a path that works without the features.

Find what the device supports

Read the support from IMGDFRenderSettingsManager:

  • GetUpscaleModeCount and GetUpscaleMode give the MGDFUpscaleMode values that the device supports. The list is empty when the device has no upscaler.
  • GetMaxGeneratedFrames gives the largest number of generated frames per rendered frame. It is 0 when frame generation is not supported.
  • GetLowLatencyModeCount and GetLowLatencyMode give the supported MGDFLowLatencyMode values. MGDF_LOW_LATENCY_OFF is always in the list.

The host gets the support when it creates the device. Before that, the lists report no support. Read them in RTBeforeFirstDraw, and read them again in RTDeviceReset, because a new device can have different support. Use the same lists to show the settings to the user: show only the modes in the lists.

{% highlight c++ %} BOOL __stdcall Module::RTBeforeFirstDraw(IMGDFRenderHost *host) { MGDF::ComObject settings; host->GetRenderSettings(settings.Assign()); _upscaleModes.clear(); for (UINT64 i = 0; i < settings->GetUpscaleModeCount(); ++i) { MGDFUpscaleMode mode; if (settings->GetUpscaleMode(i, &mode)) _upscaleModes.push_back(mode); } _maxGeneratedFrames = settings->GetMaxGeneratedFrames(); _lowLatencyModes.clear(); for (UINT64 i = 0; i < settings->GetLowLatencyModeCount(); ++i) { MGDFLowLatencyMode mode; if (settings->GetLowLatencyMode(i, &mode)) _lowLatencyModes.push_back(mode); } return TRUE; } {% endhighlight %}

While frame generation runs, the low latency mode is at least MGDF_LOW_LATENCY_ON. Frame generation does not work with an scRGB back buffer. Set HDRFormat in GetGraphicsRequirements to MGDF_HDR_FORMAT_HDR10 if the module supports HDR output and frame generation (see HDR output).

Select a render size

The module selects the upscale mode. Use a mode from the list. Call IMGDFCommonHost::GetUpscaleRenderSize with that mode and the output size. Render the scene at the size it returns. DLAA renders at the output size. MinWidth to MaxWidth and MinHeight to MaxHeight give the range for dynamic resolution. The output size changes with the back buffer, so select the render size again in RTBackBufferChange.

{% highlight c++ %} BOOL __stdcall Module::RTBackBufferChange(IMGDFRenderHost *host) { _upscale = std::find(_upscaleModes.begin(), _upscaleModes.end(), _upscaleMode) != _upscaleModes.end(); MGDFBackBufferInfo info = {}; host->GetBackBufferInfo(&info); _renderSize = {info.Width, info.Height, info.Width, info.Height, info.Width, info.Height}; if (_upscale) { if (FAILED(host->GetUpscaleRenderSize(_upscaleMode, info.Width, info.Height, &_renderSize))) _upscale = false; } return CreateRenderTargets(_renderSize.Width, _renderSize.Height, info.Width, info.Height); } {% endhighlight %}

Low latency and frame generation settings

The user selects the low latency mode and the number of generated frames. Use SetLowLatencyMode and SetFrameGeneration on IMGDFPendingRenderSettingsChange, then release the change to apply it. SetLowLatencyMode returns FALSE for a mode that is not in the list. SetFrameGeneration returns FALSE for a value more than GetMaxGeneratedFrames. Read the current values with GetCurrentLowLatencyMode and GetFrameGeneration.

A low latency change applies on the next frame. A frame generation change makes a new swap chain, so the module gets RTBeforeBackBufferChange and RTBackBufferChange. The host keeps both values in the host.lowLatencyMode and host.frameGeneration preferences. When the device does not support a saved value, the host uses off. On some devices, vsync does not work with frame generation. On these devices the host presents without vsync while frame generation runs.

Each frame

In RTDraw the module does these steps on IMGDFRenderHost:

  1. Call SetFrameMarker with MGDF_FRAME_MARKER_SIMULATION_START before it reads the simulation state, and with MGDF_FRAME_MARKER_SIMULATION_END after it has the state. Report MGDF_FRAME_MARKER_INPUT_SAMPLE when it reads controller input. Report MGDF_FRAME_MARKER_RENDER_SUBMIT_START before it records the first command list.
  2. Call SetFrameConstants once for each used View (0 or 1) with the camera data of the frame (MGDFFrameConstants). The matrices are row-major for row vectors (v * M) and do not contain the jitter. JitterOffset is in render pixels. Set ResetHistory to TRUE after a camera cut. Each view has separate history. Use the same View in MGDFUpscaleDesc. Frame generation uses view 0.
  3. Render the scene at the render size with jitter. Then call Upscale to record the upscale into a command list.
  4. Render the post-processing and the UI at the output size. Call SetFrameGenerationInputs.
  5. Execute the command lists. Call SetFrameMarker with MGDF_FRAME_MARKER_RENDER_SUBMIT_END after the last submit.

Each MGDFFrameResource has a State. This is the state that the resource has when the GPU runs the work that uses it. The calls do not add barriers and do not change resource states. Add the barriers before the call. A zero Width or Height selects the default region.

Upscale has these rules:

  • The list must be a direct list that is recording. Create it with the SDK MGDF::D3D12CommandList helper (see GPU counters in Writing a D3D12 module). An untracked list returns E_INVALIDARG.
  • ColorIn, Depth and MotionVectors are at the render size. ColorOut is at the output size and needs unordered access. Exposure and BiasCurrentColor are optional. Without Exposure the upscaler uses automatic exposure. Set ColorHDR to TRUE if ColorIn is linear HDR color before tonemapping.
  • After the call, the descriptor heaps, root signature, pipeline state, render targets and viewports of the list are undefined. Set them again before you record more work.
  • It returns E_ILLEGAL_METHOD_CALL if SetFrameConstants was not called for that view in this frame, and E_FAIL if the upscaler failed.
{% highlight c++ %} render->SetFrameConstants(&constants); DrawScene(list); // Jittered, at the render size. TransitionUpscaleInputs(list); MGDFUpscaleDesc upscale = {}; upscale.Mode = _upscaleMode; upscale.RenderWidth = _renderSize.Width; upscale.RenderHeight = _renderSize.Height; upscale.OutputWidth = _outputWidth; upscale.OutputHeight = _outputHeight; upscale.ColorHDR = TRUE; upscale.ColorIn = {_color.Get(), D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE}; upscale.ColorOut = {_upscaled.Get(), D3D12_RESOURCE_STATE_UNORDERED_ACCESS}; upscale.Depth = {_depth.Get(), D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE}; upscale.MotionVectors = {_motion.Get(), D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE}; if (FAILED(render->Upscale(list, &upscale))) return FALSE; list->SetDescriptorHeaps(1, _heaps.AsArray()); // Bind again after Upscale. {% endhighlight %}

SetFrameGenerationInputs has these rules:

  • Call it before RTDraw returns in each frame that frame generation can use. Depth and MotionVectors are necessary. Their default region is the full resource.
  • HudlessColor and UIColorAndAlpha are optional, but frame generation gives much better results with UI when you supply them. They have the back buffer size and the back buffer encoding. UIColorAndAlpha has premultiplied color and zero alpha where there is no UI, so that the back buffer is UI.rgb + (1 - UI.a) * hudless. Its alpha needs more than 2 bits, so do not use DXGI_FORMAT_R10G10B10A2_UNORM for it.
  • Frame generation runs at present. Put each input in its State at the end of the frame's command lists. Keep its content and state until the frame is presented.
  • Pass null, or do not call it, while the game loads, is paused, or changes the world. Frame generation then stops for that frame.
  • It returns S_FALSE when frame generation is off.
{% highlight c++ %} if (_loading || _paused) { render->SetFrameGenerationInputs(nullptr); } else { MGDFFrameGenerationDesc generation = {}; generation.Depth = {_depth.Get(), D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE}; generation.MotionVectors = {_motion.Get(), D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE}; generation.HudlessColor = {_hudless.Get(), D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE}; generation.UIColorAndAlpha = {_ui.Get(), D3D12_RESOURCE_STATE_NON_PIXEL_SHADER_RESOURCE}; render->SetFrameGenerationInputs(&generation); } {% endhighlight %}

When the features are not available

The features are not available on a non-NVIDIA adapter, on WARP or another software adapter, or when the driver does not support them. In these cases:

  • The upscale mode list is empty, GetMaxGeneratedFrames returns 0, and the low latency mode list has only MGDF_LOW_LATENCY_OFF. SetLowLatencyMode and SetFrameGeneration return FALSE for any value other than off.
  • GetUpscaleRenderSize and Upscale return E_NOTIMPL.
  • SetFrameMarker and SetFrameConstants do nothing. SetFrameGenerationInputs returns S_FALSE.

The log gives the reason. You can call the frame methods on each frame without a check, but keep a render path without Upscale. For example, render at the output size and use your own anti-aliasing.

The debug overlay data (MGDFDebugOverlayData) contains the render latency and the numbers of rendered and presented frames. While frame generation runs, the presented frames are more than the rendered frames.

Ray tracing

A D3D12 module that uses DXR can ask the host if the device supports ray tracing. Call GetRayTracingSupport on IMGDFRenderSettingsManager. It returns TRUE when the device supports D3D12 raytracing tier 1.1 and shader model 6.9, which HitObject and MaybeReorderThread need. It also fills MGDFRayTracingSupport. ShaderExecutionReordering is TRUE when the device reorders shader execution (raytracing tier 1.2). Without it, MaybeReorderThread does nothing. The support follows the same rules as the upscaling lists: read it in RTBeforeFirstDraw and again in RTDeviceReset.

The user can turn ray tracing off. GetRayTracing returns the setting, and SetRayTracing on IMGDFPendingRenderSettingsChange changes it. SetRayTracing(TRUE) returns FALSE when the device does not support ray tracing. The host keeps the setting in the host.rayTracing preference. It is on by default, and the host turns it off when the device does not support ray tracing. The host does not change the back buffer or the device for this setting. The module reads it and selects its own render path.

{% highlight c++ %} MGDFRayTracingSupport support = {}; _rayTracing = settings->GetRayTracingSupport(&support) && settings->GetRayTracing(); _reorder = _rayTracing && support.ShaderExecutionReordering; {% endhighlight %}

When several adapters meet the module's requirements, the host selects an adapter that supports ray tracing before an adapter with more dedicated memory.

With HDR10 the module writes encoded values. Do these steps in the last pass that writes the back buffer:

  1. Blend the scene and the UI in linear light. Blending into the back buffer mixes encoded values, so do not use it for the UI.
  2. Tonemap to the luminance range of the display.
  3. Convert the color from Rec.709 to Rec.2020 primaries.
  4. Divide by 10000 nits and apply the PQ encode.
{% highlight c++ %} // HLSL. nits: linear Rec.2020 color in nits. float3 EncodePQ(float3 nits) { const float m1 = 0.1593017578125f, m2 = 78.84375f; const float c1 = 0.8359375f, c2 = 18.8515625f, c3 = 18.6875f; const float3 y = pow(saturate(nits / 10000.0f), m1); return pow((c1 + c2 * y) / (1.0f + c3 * y), m2); } {% endhighlight %}

For frame generation, HudlessColor and UIColorAndAlpha use the same encoding as the back buffer (PQ with HDR10).

HDR metadata

Call SetHDRMetadata on IMGDFRenderHost to tell the display the light levels of the content (MGDFHDRMetadata, in nits). The values stay in effect after resizes and back buffer changes. They apply only to HDR10 output. Pass null to clear the metadata. SetHDRMetadata returns E_INVALIDARG and keeps the old values if a value is out of range: MaxCLL from 0 to 65535, MaxFALL from 0 to MaxCLL, mastering maximum more than 0 and up to 10000, and mastering minimum from 0 to less than the mastering maximum.

{% highlight c++ %} MGDFOutputDisplayInfo display = {}; settings->GetCurrentOutputDisplayInfo(&display); // The tonemapper limits the output to this peak. const float peak = display.MaxLuminance > 0.0f ? display.MaxLuminance : 1000.0f; MGDFHDRMetadata metadata = {}; metadata.MaxContentLightLevel = peak; metadata.MaxFrameAverageLightLevel = (std::min)(display.MaxFullFrameLuminance, peak); metadata.MaxMasteringLuminance = peak; metadata.MinMasteringLuminance = display.MinLuminance; host->SetHDRMetadata(&metadata); {% endhighlight %}

Running a game

The program that starts the game depends on the build:

  • Installed game. The game shortcuts start updater.exe. After the update check, the updater starts core.exe. It gives its own command line arguments to core.exe without change.
  • Store build. The store client starts core.exe. Do not ship updater.exe in a store build.
  • Development. Run core.exe directly. You can then attach the Visual Studio debugger.

Do not run updater.exe as administrator. An updater that runs as administrator stops and does not start the game.

You do not have to keep the game in the runtime folder during development. To run a game folder from another location, give the folder to core.exe:

core.exe -gamediroverride "C:\dev\mygame\game"

The folder must have the same layout as the /game folder: /bin, /content, and game.json.

MGDF stores logs, saved games, and preferences in %LOCALAPPDATA%\MGDF\1\<gameUid>. With the flag -userdiroverride, MGDF stores these files in a /user folder next to the game folder. For example, with -gamediroverride c:\mygame\game and -userdiroverride, MGDF uses c:\mygame\user. Without -gamediroverride, MGDF uses user\<gameUid> in the core.exe folder.

Each argument -name also has an environment variable MGDF_NAME. Command line arguments have priority over environment variables. Before it reads the arguments, the core reads the file .env in the core.exe folder, if it is present. Each line of this file is KEY=VALUE. Blank lines, comment lines that start with #, and quoted values are permitted. A value in .env does not replace an environment variable that is already set. Use .env to keep development settings out of the command line:

MGDF_LOGLEVEL=log_high
MGDF_GAMEDIROVERRIDE="C:\dev\mygame\game"
MGDF_USERDIROVERRIDE=1

For all the arguments, see the command line options.

Distributing a game

For an installed game, you supply an installer, an update service, and the services for crash reports and statistics. A store build uses the store client to install and update the game. A store build can also use crash reports and statistics.

Installing

MGDF does not install games. Supply an installer, for example an NSIS installer. The installer must do these steps:

  1. Copy the runtime files and the /game folder to the install folder in the MGDF folder layout. Do not copy game/game.json in this step.
  2. Run dependencies\vc2022_redist.x64.exe /install /quiet /norestart. This installs the Visual C++ runtime when it is not installed. Exit codes 0, 1638 (a newer version is installed), and 3010 (a restart is necessary) are not errors.
  3. Make sure that .NET Framework 4.8 is installed. The updater and the crash reporter need it. If it is not installed, install it or tell the player to install it.
  4. Create the shortcuts. The shortcuts start updater.exe.
  5. Write the uninstaller and the uninstall record in the registry.
  6. Write game/game.json last, after all the other steps are successful.

The updater uses game.json to find the end of an update. When game.json has the new version, the update is complete. If a step fails, stop the installer with a non-zero exit code before you write game.json. Return exit code 0 when the install is successful. Exit codes 3010 and 1641 (restart) also mean success.

The updater starts the installer without elevation. If the installer needs administrator rights, it must ask for them. For NSIS, use RequestExecutionLevel admin. The installer must also accept the arguments that your update service supplies (see Updating).


Example NSIS install script (for a game named 'New Game')

The runtime folder contains the files of the MGDF runtime zip. The game folder contains your /game folder. Put ndp48-web.exe (the .NET Framework 4.8 web installer) beside the script. Build the installer with makensis /DGAME_VERSION=1.2.3 installer.nsi.

!include "MUI2.nsh"
!include "FileFunc.nsh"
!include "LogicLib.nsh"

!ifndef GAME_VERSION
  !error "GAME_VERSION is required"
!endif
!define UNINSTALL_KEY "Software\Microsoft\Windows\CurrentVersion\Uninstall\NewGame"

Name "New Game"
OutFile "NewGameSetup.exe"
InstallDir "$PROGRAMFILES64\NewGame"
InstallDirRegKey HKLM "${UNINSTALL_KEY}" "InstallLocation"
RequestExecutionLevel admin

!insertmacro MUI_PAGE_DIRECTORY
!insertmacro MUI_PAGE_INSTFILES
!insertmacro MUI_UNPAGE_CONFIRM
!insertmacro MUI_UNPAGE_INSTFILES
!insertmacro MUI_LANGUAGE "English"

; Stop with exit code 4 if the last step failed.
!macro CheckInstallStep
  IfErrors 0 +3
    SetErrorLevel 4
    Quit
!macroend

Function .onInit
  SetRegView 64
  SetShellVarContext all
  InitPluginsDir
FunctionEnd

Section "Install New Game"
  ; The updater and the crash reporter need .NET Framework 4.8.
  ReadRegDWORD $0 HKLM "SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full" "Release"
  ${If} $0 < 528040
    SetOutPath "$PLUGINSDIR"
    File "ndp48-web.exe"
    ExecWait '"$PLUGINSDIR\ndp48-web.exe" /q /norestart' $0
    ${If} $0 == 3010
    ${OrIf} $0 == 1641
      SetRebootFlag true
    ${ElseIf} $0 != 0
      IfSilent +2
        MessageBox MB_OK|MB_ICONSTOP "Cannot install .NET Framework 4.8. Setup will stop."
      SetErrorLevel 2
      Quit
    ${EndIf}
  ${EndIf}

  ClearErrors
  SetOutPath "$INSTDIR"
  File /r "runtime\*"
  !insertmacro CheckInstallStep
  ExecWait '"$INSTDIR\dependencies\vc2022_redist.x64.exe" /install /quiet /norestart' $0
  !insertmacro CheckInstallStep
  ${If} $0 == 3010
    SetRebootFlag true
  ${ElseIf} $0 != 0
  ${AndIf} $0 != 1638
    IfSilent +2
      MessageBox MB_OK|MB_ICONSTOP "Cannot install the Visual C++ runtime. Setup will stop."
    SetErrorLevel 3
    Quit
  ${EndIf}

  SetOutPath "$INSTDIR\game"
  File /r /x game.json "game\*"
  !insertmacro CheckInstallStep

  SetOutPath "$INSTDIR"
  WriteUninstaller "$INSTDIR\Uninstall.exe"
  CreateDirectory "$SMPROGRAMS\New Game"
  CreateShortcut "$SMPROGRAMS\New Game\New Game.lnk" "$INSTDIR\updater.exe"
  CreateShortcut "$DESKTOP\New Game.lnk" "$INSTDIR\updater.exe"
  CreateShortcut "$SMPROGRAMS\New Game\Uninstall.lnk" "$INSTDIR\Uninstall.exe"
  WriteRegStr HKLM "${UNINSTALL_KEY}" "DisplayName" "New Game"
  WriteRegStr HKLM "${UNINSTALL_KEY}" "DisplayVersion" "${GAME_VERSION}"
  WriteRegStr HKLM "${UNINSTALL_KEY}" "InstallLocation" "$INSTDIR"
  WriteRegStr HKLM "${UNINSTALL_KEY}" "UninstallString" '$\"$INSTDIR\Uninstall.exe$\"'
  WriteRegStr HKLM "${UNINSTALL_KEY}" "QuietUninstallString" '$\"$INSTDIR\Uninstall.exe$\" /S'
  WriteRegDWORD HKLM "${UNINSTALL_KEY}" "NoModify" 1
  WriteRegDWORD HKLM "${UNINSTALL_KEY}" "NoRepair" 1
  !insertmacro CheckInstallStep
  ${GetSize} "$INSTDIR" "/S=0K" $0 $1 $2
  WriteRegDWORD HKLM "${UNINSTALL_KEY}" "EstimatedSize" $0
  !insertmacro CheckInstallStep

  ; game.json marks a complete install. Write it last.
  SetOutPath "$INSTDIR\game"
  File "game\game.json"
  !insertmacro CheckInstallStep
SectionEnd

Function un.onInit
  SetRegView 64
  SetShellVarContext all
FunctionEnd

Section "Uninstall"
  Delete "$DESKTOP\New Game.lnk"
  RMDir /r "$SMPROGRAMS\New Game"
  DeleteRegKey HKLM "${UNINSTALL_KEY}"
  RMDir /r "$INSTDIR"
SectionEnd

With this script, an update service can use the installer arguments ["/S", "/D={installDir}"].

Updating

To turn on updates, set updateService in game.json to the URL of your update service. Each time the updater starts, it sends a GET request to this URL. The service returns a JSON document that describes the newest version. For the fields, see the update service reference.

{% highlight json %} { "version": "1.2.3", "installerUrl": "https://www.example.com/NewGameSetup_1.2.3.exe", "sha256": "<64 hexadecimal digits>", "installerArguments": ["/S", "/D={installDir}"] } {% endhighlight %}

These rules apply:

  • The update service URL and installerUrl must use HTTPS. Redirects must also use HTTPS. For local tests, HTTP to a loopback IP address such as 127.0.0.1 is permitted.
  • The update service must reply in 5 seconds. The response is limited to 64 KiB.
  • The updater compares the SHA-256 hash of the downloaded installer with sha256. It does not run an installer with a different hash. The updater does not check installer signatures.
  • The installer has no size limit and the download has no time limit. The download stops if no data arrives for 60 seconds.

The updater starts the game and shows no message in these cases: game.json has no updateService, the check fails, or the version from the service is not newer than the version in game.json.

When a newer version is available, the updater shows a dialog with two buttons:

  • Update now downloads the installer. During the download, Cancel stops the download and starts the current version of the game.
  • Later starts the current version of the game.

If the download or the hash check fails, the updater shows "Cannot download the update." and then starts the current version.

After the download, the updater closes and runs the installer with the installer arguments. Then:

  • If the installer is successful, the updater starts the new version of the game.
  • If the player refuses the elevation prompt, the updater starts the current version of the game. During a repair, the game stays closed.
  • If the game or its crash dialog is open, the updater shows "Close the game and its crash report window, then try the update again." It does not run the installer, and it starts the current version.
  • If the installer fails, the updater shows "Cannot install the update. Run the updater again to repair the game." The game does not start. At the next start, the updater shows "The update did not finish. Install the update to repair the game." The game starts again only after the install is complete.

Only one update can run for an install folder at a time. A second updater shows "An update is in progress." and does not start the game.

Crash reports

To turn on crash reports, set crashReportService in game.json to the URL of your crash report service. Ship crashreporter.exe beside core.exe. Set privacyPolicy to add a privacy policy link to the dialog. Without a crash report service or crashreporter.exe, a crash shows a short error message that gives the location of the log file. The flag -hideerrors stops this message.

The crash dialog shows only after a crash:

  • an unhandled exception in the core or in the module,
  • a fatal error, for example a call to FatalError on IMGDFCommonHost,
  • an exit of core.exe with an exception status code (0xC0000000 and higher, but not 0xC000013A).

A normal exit and all other exit codes show no dialog and send no report. A failure during startup uses exit code 1.

The dialog tells the player that the game stopped unexpectedly. When there is error text, the dialog shows it in a read-only box with a Copy button. The error text has a maximum of 2048 characters. For a fatal error, the text gives the sender and the message. The dialog has two buttons: Send report and Don't send. If the report cannot be sent, the dialog shows "Cannot send the report. Please try again later."

The report is a zip file with these files:

  • log.txt: the MGDF version, the Windows version and architecture, the processor count, the game uid and version, the crash details, and the game log.
  • minidump.dmp: a minidump of core.exe, when one is available.

The flag -hideerrors stops the dialog and the report. The crash reporter then writes the minidump as crash-<id>.dmp in the game user folder and keeps it.

For the service contract, see the crash report service reference.

Statistics tracking

MGDF can send statistics from play sessions to a statistics service. Set statisticsService in game.json to the URL of your service. The core argument -statisticsendpointoverride replaces this URL. Without a URL, MGDF sends no statistics.

The game supplies the values. Get the IMGDFStatisticsManager interface with GetStatistics on IMGDFCommonHost. Call PushString to send a name, a value, and optional tags. Call PushMetric to send the current value of a metric.

MGDF does not ask the player for permission. The game owns the consent controls: ask the player, keep the choice, and push values only after the player agrees. Show your privacy policy with this choice.

Each value has a timestamp in milliseconds from the start of the session. All the values from one session have the same session id. For the service contract, see the statistics service reference.
